MLOPS Testing Types
===================
- Pipeline validation: Dry run on the model to check whether its running, can it take input & give a output. Do we have the ability to train the model. This will be done on a dev environment.
- Model Validation: Split the dataset into 80%-20%. Train the Model with 80% dataset & use the 20% of dataset to evaluate. This will be done in QA environment.
   # Is it connecting to dependencies (database, kafka etc), is it able to pull or push data
- Inference Testing: End-End Application testing to check if Model is working in the Product Ecosystem. You can do Load/Performance tests.
- Shadow Testing: By passing live production data, check whether your Model is predicting properly.

Dockerfile
==========
* Special file in which we give the instructions on how to create a Docker Image.
 - Automates the Image creation on the background
 - uses existing layer from cache (/var/lib/docker)

Imagename = Reponame:Tagname # default tag is latest
Image = <Registry>/<ImageName>:<TagName>

INSTRUCTION    COMMAND
===========    =======
FROM         <BaseImage>        # image for creating the intermediate container
RUN          <command>          # instruction to run OS cmd inside the intermediate container
USER         <USERNAME>                      # sets the default user
WORKDIR      <PATH>                          # sets the default working dir
COPY         <SRC> <DEST>                    # copies file from docker host to image
EXPOSE       <PORT#>
CMD          ["executable","arg1","arg2"]    # user cmd will override the default cmd
ENTRYPOINT   ["executable","arg1","arg2"]    # always runs default cmd, user cmd is taken as arguments

Healthchecks
============
* livenessprobe
 - container gets recreated if check fails
* readinessprobe
 - doesnt send the traffic to that pod

- What cmd/script to run
- how frequently to run
- we should make sure the script is available inside the Image & it returns appropriate return code
- 0 return indicates container is healthy, non-zero indicates container is not healthy

healthcheck.yml
---------------
kind: Deployment
apiVersion: apps/v1
metadata:
   name: mydeploy
spec:
   replicas: 1
   selector:       
    matchLabels:
     name: deployment
   template:
     metadata:
       name: testpod8
       labels:
         name: deployment
     spec:
      containers:
        - name: main
          image: httpd
          ports:
           - containerPort: 80
          livenessProbe:                  # define the health check
           exec:
             command:                     
             - ls
             - /tmp/lp
           initialDelaySeconds: 30  
           periodSeconds: 5         
           timeoutSeconds: 10
          readinessProbe:                 # define the health check
           exec:
            command:     
            - ls
            - /tmp/rp
           initialDelaySeconds: 30  
           periodSeconds: 5    
           timeoutSeconds: 30

Container Pattern:
1. A type of container which gets created first before the main container i.e init container

FINTECH (B2B) Microservices Architecture
========================================
ledger service  - (Java)              
payment         - (Golang) 
fraud           - (Python)       
notification    - (Node.js)     
bff             - (Node.JS)
Dashboard/Checkout UI - (React/Vue.js)    

1. Merchant Dashboard: The business owner’s control panel for checking daily sales, refunds, and "Settle" (payout) status.
2. Checkout UI: The "Digital Cashier" that pops up inside apps like Zomato to collect card or UPI details safely.
3. BFF (Backend for Frontend): The BFF acts as a single personal assistant that bundles messy backend data for faster screen loading and securely forwards checkout clicks directly to core payment services to process the money.
4. Ledger Service: The "Master Accountant" that maintains a permanent, immutable record of every transaction to ensure no money goes missing. 
5. Payment Gateway: The "Bank Runner" that carries encrypted card details to the big banks to move the actual money..
6. Fraud Detection Service: The "Detective" that analyzes patterns in real-time to block suspicious or impossible transactions
7. Notification Service: The "Postman" that delivers the "Payment Successful" SMS, WhatsApp, or push alert.

8. Why these specific Databases?
 ## - Ledger & Payment requires ACID Compliance - ##
      ------------------------------------------
  a. Atomicity (All or Nothing) - Without it if the system crashes halfway, the money might leave your account but never reach your friend. Ensure whole transaction rolls back.
  b. Consistency (Following the Rules) - If your account balance cannot be negative, the database will automatically reject a payment that would take you below zero.
  c. Isolation (No Double-Counting) - If you have ₹1000 and try to buy two different items worth ₹600 at the exact same millisecond, the database processes them one by one. It won't let both go through just because they happened at the same time.
  d. Durability (The Permanent Ink) - Once you see "Payment Successful," that record is written to the hard drive (not just the temporary memory/RAM), so it’s there when the system reboots.

INFO:
- Both Maice/Comprehend engines use the same underlying AWS machine learning models to detect sensitive information.
  Personal Data: Full Names, Mailing Addresses, Phone Numbers, Email Addresses.
  Financial Data: Credit Card Numbers, Bank Account Details, Routing Numbers.
  National Identifiers: US Social Security Numbers (SSN), India Aadhaar Cards, Permanent Account Numbers (PAN).
  Credentials: AWS Access Keys, Secret Tokens, Private Encryption Keys.

- Amazon Comprehend is AIOps applied to Data Ingestion (Real-Time Inline Cleansing) i.e handles real-time inline data
- AWS Macie is AIOps applied to Infrastructure Security (Continuous Account-Wide Scanning and Auditing), which provides intelligent cloud operations, compliance monitoring, and automated threat discovery.

1. AWS Macie tells you Where the PII is inside the Cloud (trigger Macie whenever you want/daily, but only as a complete bucket scan)
Macie generates a Finding Report. It tells you: "Inside bucket X, in file Y, on line 42, I found an Email Address." It does not give you the actual email text string. Your Lambda function must use that path metadata to open the file and scrub that specific line.

2. Amazon Comprehend tells you What the PII text actually is (event-driven, object-level scanning)
Comprehend scans the raw text string directly in memory and gives you precise character offsets. It tells you: "I found an EmailAddress starting at character 150 and ending at character 174, and the text string is user@email.com." This makes writing redactions simple, as you can replace those exact string indexes in memory instantly.

## MODULE 5 - Continuous Delivery Pipeline ##
## --------------------------------------- ##

* Unit Tests: Performed by developers to check the files modified by them for a particular functionality or feature is working before they commit the code
* Functional Tests: Performed by QA to check the app/microservice has the newly developed/modified functionality is working (they take all the files in the app)
* Integration Tests: Performed by QA after functional test to check whether all the induvial newly developed / modified functionality is working 
* Regression Tests: Performed by QA after Integration test to check whether the newly created functionality is working fine with older/existing functionality
* UAT: Performed by QA/Ops after Regression test to check end-end functionality of the app/microservice in a real-world scenario (in an env similar to production)

Development -> Build App (microservice) -> Deploy App (run) -> Test

Continuous Development (Dev) -> Continuous Integration(We) -> Continuous Deployment(We) -> Continuous Testing(QA)

Feature branch: (dev) Code+Unit-test -> (We) Build -> (We) Deploy to QA env -> (QA) Functional test
                                                           
Main Branch: (Dev) merge from FB to Main -> (We)Build -> (We) Deploy to QA env -> (QA) Integration/Regression test
                                                      -> (We) Deploy to STAGE env -> (QA) UAT test
                                                      -> (We) Deploy to PROD env -> RELEASE

INFO: 
----
1 Build Pipeline for each Feature Branch (On Push), 1 Build Pipeline for Main Branch (Pull_request)
1 Deployment Pipeline for QA Deployment, 1 Deployment Pipeline for Stage & Prod

Feature Branch: Benchmark for quality profile is 70-80% codecoverage, 5% code duplication, B type vuln, No Critical Vuln
Main Branch: Benchmark for quality profile is 90% covderage, No Critical/High vuln, A type vuln

Configuration Layer: App startup property files (db/kafka/cache server details, creds, log files, arguments), certificates

- The ledger service opens a MySQL database transaction. It locks the user's account row, checks if they have enough money, subtracts the amount, adds it to the merchant's balance, and saves a tiny text record of the transaction.
- The ledger service takes the huge, messy JSON response received from the bank networks, packages it up, and uploads it to S3 as a file. If the merchant needs a PDF receipts, the service generates it and saves it directly to S3 too.

High Availability: Zero downtime
Disaster Recovery: Recover your service/app without loss of data
Autoscaling of DB server

#- Why RDS? -#
   ========
1. we define the type of server & AWS manages creation of server, install DB & maintain it
2. High Availability setup by RDS
3. Automated Patching
4. DB Upgrades
5. Automated backups

RDS Proxy Benefits:
 - Reduce database load by pooling connections
 - Automatic failover
 - Enhanced security by integrating with AWS secret manager or AWS IAM authentication

# We upgrade lower environments using in-place method & higher envs using blue-green method
 - We upgrade major version once in 1-2 years

# Version upgrade & Vertical scaling for CPU/RAM happens using blue-green method
# When ledger system encounters high read traffic concurrency, only then we do Horizontal scaling by decoupling your database reads from your database writes and add 3 read replicas (more as we need)

  ## INFO- This should be executed against Data network & in the 3 private subnets created for DB

## -- Create AWS RDS MYSQL Database -- ##
# git clone https://github.com/wezva-fintech/terraform-modules.git #
$ cd rds-mysql-bluegreen
# Step 1: New DB creation
$ terraform init
$ terraform plan -var="source_db_engine_version=8.4.13" -out db8.4.13
$ terraform apply db8.4.13

# Step 2: DB Upgrade
$ terraform plan -var="source_db_engine_version=8.0.43" -var="trigger_green_creation=true" -var="target_db_engine_version=8.4.4" -out dbupgrade8.4.4
$ terraform apply "dbupgrade8.4.4"

# Step 3: DB DNS Switch
$ terraform plan -var="source_db_engine_version=8.0.43" -var="trigger_green_creation=true" -var="target_db_engine_version=8.4.4" -var="trigger_switchover=true" -out dbswitchdns
$ terraform apply "dbswitchdns"

# Step 4: Delete Older DB
$ terraform plan -var="source_db_engine_version=8.0.43" -var="trigger_green_creation=true" -var="target_db_engine_version=8.4.4" -var="trigger_switchover=true" -var="delete_source_db=true" -out dbdeleteblue
$ terraform apply "dbdeleteblue"

# Step 5: Destroy all
$ terraform destroy -auto-approve

## -- Create secret to download images from ECR -- ##

Install AWS Cli:
 $ curl "https://awscli.amazonaws.com/awscli-exe-linux-x86_64.zip" -o "awscliv2.zip"
 $ sudo apt install unzip && unzip awscliv2.zip
 $ sudo ./aws/install --bin-dir /usr/bin --install-dir /usr/bin/aws-cli --update
 $ aws --version

$ export AWS_ACCESS_KEY_ID=<YOUR_ACCESS_KEY_ID>
$ export AWS_SECRET_ACCESS_KEY=<YOUR_SECRET_ACCESS_KEY>
$ ACCOUNT=$(/usr/bin/aws sts get-caller-identity --query 'Account' --output text)
$ REGION=ap-south-1
$ TOKEN=$(/usr/bin/aws ecr get-authorization-token --region $REGION --output text --query 'authorizationData[0].authorizationToken' | base64 -d | cut -d: -f2)

# Create a new namespace for the app to deploy
$ kubectl create ns demo
$ kubectl create secret docker-registry ecr-secret -n demo\
   --docker-server=$ACCOUNT.dkr.ecr.$REGION.amazonaws.com \
   --docker-username=AWS \
   --docker-password="$TOKEN" \
   --docker-email=scmlearningcentre@gmail.com
